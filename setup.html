# Наряд-допуски — Google-вход и личный Google Диск

## Что изменилось
Новые пользователи входят и регистрируются через Google. После первого входа один раз указывают подразделение (ЦТО МС, ЦТПСР, ЦЭиК) и телефон. Имя подставляется из Google и может быть уточнено в профиле.

Доступны два пути: загрузить готовый подписанный НД или заполнить и распечатать один из трёх шаблонов. В обоих случаях перед открытием нужно загрузить все подписанные страницы и подтвердить комплектность.

Сервер создаёт на личном Google Диске пользователя папку «Наряд-допуски ДЭСД», а в ней папку региона и наряда. В ней сохраняются все подписанные фото/PDF и JSON с номером, регионом, подразделением, производителем, телефоном, временем, статусом и заполненным HTML-бланком (если он был). После успешного сохранения на Диск наряд открывается в реестре. При ошибке Диска наряд не открывается. При закрытии обновляется JSON на Диске, затем общий реестр. Наряд закрывает только владелец учётной записи, который его открыл.

Файлы остаются приватными на Google Диске; приложение не создаёт разрешений «доступно всем по ссылке». Однако второй сайт намеренно показывает подписанные страницы и телефон всем его посетителям: сервер получает именно эти файлы с разрешения владельца и передаёт в мониторинг. Посторонние файлы Диска не индексируются и не публикуются. Проверка настоящих подписей не автоматизирована; её подтверждает производитель.

## Зачем по-прежнему нужен сервер
GitHub Pages размещает интерфейс, но не хранит секрет Google и не выполняет серверный OAuth. Каждому региону нужен постоянно работающий сервер Node.js 24+ или Docker с HTTPS.

Сервер хранит небольшой индекс НД (метаданные, статусы, привязка к владельцу, идентификаторы файлов), пользователей, сеансы и зашифрованное разрешение Google. Подписанные файлы и заполненный бланк новых НД хранятся на личном Google Диске, а не в папке загрузок сервера. Индекс нужен второму сайту для сводки по всем пользователям. У каждого региона — свой сервер и DATA_DIR; оба сайта обращаются к ним через общий config.json.

Старые локальные записи не удаляются. Для них оставлено чтение прежних файлов и проверка владельца. Google-учётки автоматически не объединяются с прежними локальными логинами по совпадению имени или почты; миграцию старых владельцев нужно делать отдельно, если такие записи уже использовались в работе.

## 1. Настроить Google Cloud для региона
1. Открыть https://console.cloud.google.com/ и создать/выбрать проект.
2. Включить **Google Drive API**.
3. Настроить OAuth-приложение в Google Auth Platform (либо OAuth consent screen): название, контакт администратора и аудитория. Для разных личных Gmail нужна внешняя аудитория; внутренняя подходит только пользователям соответствующей организации Google Workspace.
4. В доступах указать openid, email, profile и https://www.googleapis.com/auth/drive.file. drive.file даёт доступ только к файлам, используемым приложением; полный доступ ко всем файлам Диска не нужен.
5. Создать OAuth Client ID типа **Web application**.
6. Добавить точный Authorized redirect URI:
   https://АДРЕС-СЕРВЕРА-РЕГИОНА/oauth/google/callback
   Это адрес сервера региона, а не GitHub Pages.
7. Получить Client ID и Client secret. Секрет задаётся только на сервере, не в HTML, JS, config.json, GitHub и не в переписке.
8. В режиме Testing добавить тестовых пользователей Google. Внешнее приложение в Testing с Drive-разрешением может выдавать refresh token со сроком 7 дней. Для длительной общей работы перевести приложение в Production и выполнить требования Google к публикации. Организация Google Workspace может ограничивать сторонние приложения; это разрешает её администратор.

Официальные инструкции:
- https://developers.google.com/identity/protocols/oauth2/web-server
- https://developers.google.com/workspace/drive/api/guides/api-specific-auth

## 2. Настроить сервер региона
Папка backend содержит server.mjs, google-drive.mjs, Dockerfile и compose.yaml.

В compose.yaml указать:
- REGION — точное имя региона из regions.json, например Актюбинский ДЭСД.
- ALLOWED_ORIGINS — домены первого и второго сайта через запятую, со схемой https://, без пути и завершающего слеша.
- FRONTEND_URL — полный адрес папки ПЕРВОГО сайта, с путём и завершающим слешем. Например https://mamatovasan.github.io/NDsite/ . Возврат после Google-входа идёт именно сюда.
- GOOGLE_REDIRECT_URI — тот же точный callback, который добавлен в Google Cloud.
- DATA_DIR — отдельное постоянное хранилище региона.

Скопировать google.env.example в .env на сервере. Подставить Client ID, Client secret и ключ шифрования. .env не загружать в публичный GitHub.

Ключ шифрования (один раз) сгенерировать на сервере:
```
node -e "console.log(require('node:crypto').randomBytes(32).toString('base64'))"
```
Сохранить как TOKEN_ENCRYPTION_KEY. Ключ нужен для расшифровки разрешений Google; не менять при обычном обновлении сервера. Сохранить его вместе с защищённой резервной копией. Потеря ключа потребует повторного Google-входа пользователей.

Запуск в папке backend:
```
docker compose up -d --build
```
Настроить действительный HTTPS-сертификат и reverse proxy на 127.0.0.1:8080. Для nginx задать client_max_body_size 36m и proxy_read_timeout 180s. Адрес и сертификат предоставляет администратор региона. /health должен вернуть правильный регион и googleConfigured:true.

Без Docker: Node.js 24+, задать те же переменные окружения и запустить node server.mjs через systemd/другой менеджер процессов. Компьютер, который выключают, не подходит для общего сервиса.

## 3. Настроить GitHub Pages
На первом сайте заменить app.js и setup.html из обновления. На втором сайте текущие monitor.html и regional-monitor.js уже умеют показывать файлы через сервер — менять их для Google Диска не требуется.

Указать адреса серверов в config.json, например:
```
{"endpoints":{"Актюбинский ДЭСД":"https://nd-aktobe.example.kz"}}
```
Заменить пример своим реальным адресом. У обоих сайтов должен быть одинаковый config.json. Если они на разных доменах, скопировать файл на оба хостинга. Локальная настройка адресов в браузере не синхронизируется между посетителями и доменами.

Повторить настройку для каждого региона. Можно использовать отдельные проекты Google Cloud каждого региона. У каждой базы и ключей должны быть свои ответственные администраторы.

## 4. Проверить первый рабочий вход
1. Открыть первый сайт и выбрать регион.
2. Нажать «Войти / зарегистрироваться через Google».
3. Выбрать учётку на странице Google и разрешить сохранение файлов приложения на Диске.
4. Указать подразделение и телефон.
5. Открыть тестовый НД с тестовой подписанной страницей.
6. Проверить появление папки и JSON на своём Google Диске.
7. На втором сайте проверить номер, подразделение, телефон и просмотр файла.
8. Закрыть НД с первого сайта и проверить статус на втором и в JSON на Диске.

Пока Google OAuth и региональные серверы не настроены, Google-вход и сохранение на Диск не работают. Не вводите Client secret в интерфейс сайта или в чат. Для настройки достаточно сообщить публичные адреса первого сайта и сервера; секреты вводятся администратором на сервере.

## Эксплуатация
- Google-пароль приложение не получает. В браузере хранится временный сеанс приложения, а не Google refresh token.
- Google refresh token шифруется AES-256-GCM на сервере. Для чтения разрешённых файлов, когда владелец вышел из сайта, используется выданное Google offline-разрешение.
- Если владелец отзовёт разрешение, удалит файлы или у него закончится место, появится ошибка Диска. Метаданные уже открытых НД сохраняются в мониторинге; файлы могут стать недоступны. Нужно повторно войти через Google/восстановить файл/освободить место.
- Сервер не даёт гарантии хранения после удаления документа самим владельцем. Для обязательного корпоративного архива требуется отдельная политика хранения.
- Резервировать базу регионального индекса и ключ шифрования отдельно и проверять восстановление. Старые локальные файлы, если они были, также резервировать.
- Мониторинг обновляется каждые 30 секунд. Недоступные регионы показаны прочерком, итог помечается неполным.

## Проверки кода
```
node verify.mjs
```
Проверка использует временную базу и имитацию Google API. Проверяет одноразовые состояния входа, защиту подтверждения браузером, шифрование, сохранение файлов на Диск, права владельца, мониторинг, синхронизацию закрытия и ошибки загрузки. Она не выполняет вход в настоящий Google. Реальная сквозная проверка требует Client ID/secret и сервера с HTTPS и должна быть выполнена по шагу 4.
